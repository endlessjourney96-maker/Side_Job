2026-09-12、「スキル作りながら副業収入を作る」流れの一環として作成。[[spot-consulting-kit]]が「単価の高いスポット相談（Asset/Consulting案件）」を扱うのに対し、こちらは「テキストベースで完結する、比較的単価は低いが即金性の高い受託案件（Cash/Training案件）」を扱う。両方とも同じ[[project_side_income_5man_goal]]（月5万円）の一部として、`spot-consulting/収益トラッカー.md`の「経路」列にまとめて記録する。

**2026-09-12、ChatGPT側で並行検討されていた「副業自動化PM」フレームワーク（`knowledge/inbox/chatgpt/2026-09-12.md`）を統合。** 2026-09-13、ChatGPT側からの提案で役割分担を正式に確定（下記「ChatGPTとの役割分担」参照）。貼り付け時の文字化けに注意（[[feedback_chatgpt_handoff_encoding]]参照）。

## ChatGPTとの役割分担（2026-09-13確定）

「案件入口駅＝ChatGPT」「制作・納品駅＝A-3班（このスキル）」、間に採算判定・人間承認の信号を置く、という設計。探索担当と制作担当を完全分離せず、実績を相互にフィードバックし合う。

**ChatGPT側（案件探索・一次評価）**：案件候補収集、内容要約、経験・スキルとの適合度判定、報酬/工数/難易度/リスクの一次評価、応募/保留/見送りの仮判定、応募文のたたき台、案件傾向分析、過去の応募結果を次の探索条件へ反映

**A-3班＝このスキル（技術・受託実行側）**：技術的な実現可否判断、必要ツール/AI/API等の選定、概算工数・実装方法・納品物の整理、自動化できる範囲/人間作業が必要な範囲の判定（②のJob Scoutスコアリングが担当）、受注後の設計・制作・テスト・納品（④⑤）、実案件から得たノウハウのSkill化（⑨）、再利用可能なテンプレート/自動化部品の整備。実務上は`.claude/agents/`のサブエージェント3人（`intake-scout`＝②の判定、`proposal-writer`＝④⑤の作成、`qa-checker`＝⑥の検品）に分業して並列実行できる。

**共同判断**：応募するかどうかの最終判断、価格設定、納期、技術的リスクが高い案件、個人情報・機密情報・外部サービスへのアクセスが必要な案件

**理想の流れ**：案件発見 → ChatGPTで一次評価 → A-3で技術評価（②③） → 採算・リスク判定 → 応募文作成（④） → 人間確認 → 応募 → 受注 → A-3で制作（⑤⑥） → ChatGPTで文章・説明・品質レビュー → 人間確認 → 納品 → 振り返り（⑨） → Skill/テンプレートへ反映（⑩）

**双方向フィードバックのループ**：`市場 → ChatGPT → A-3 → 実績 → ChatGPT → 次の市場探索`。A-3側の実行知見（この種類は◎分自動化できた、この単価以下は割に合わない等）は⑨のLearning Loop経由で`knowledge/a3-execution-learnings.md`に書き出す（Public repoで追跡・ChatGPT側から参照可能）。ChatGPT側の市場トレンド（この種の案件が増えている等）は`knowledge/inbox/chatgpt/YYYY-MM-DD.md`経由でA-3側に届き、①②の判断基準・除外条件の更新に反映する。

## 全体Workflow

```
DISCOVER → SCORE → PROPOSAL DRAFT → HUMAN APPROVAL → APPLY → INTAKE
→ EXECUTE SKILL → CRITIC/QA → HUMAN GATE → DELIVER → MEASURE → LEARN → PACKAGE → DISCOVER
```

このスキルの②〜⑥がDISCOVER〜DELIVERを担当する。MEASURE以降は⑦収益トラッキングと⑧Learning Loopで扱う。「自動化ツールを作ること」自体が目的ではなく、案件そのものをR&D環境として使い、稼ぎながらSkillを育てるのが狙い。

## できないこと（Human Gate・必ず人間承認）

以下は対外的なコミットメントが発生する行為であり、AIが勝手に行わない。必ずユーザー本人が行う：
応募送信／見積価格確定／契約／顧客への最終納品／外部公開／課金／アカウント変更／ポートフォリオ公開判断

クライアントとのやり取りは「下書き作成→ユーザー確認→送信」の順を必ず守る（`knowledge/lessons-learned.md`のメール対応原則と同じ）。

## ① 対象外の明確化

**明確に除外**：コーディング技術を人に教える講師・プログラミングメンター・スクール講師・コーディング教材制作。Claude Code等を**実務ツールとして使う**仕事はOK。AI/DX・AIエージェント・業務改善の活用方法を教える仕事は対象だが、「コードの書き方を教える」が中心なら対象外。

**低期待値のため原則見送り**：1記事100〜500円級、文字起こし100円/本級、コピペ中心、AI画像大量生成だけ、AI利用可であること以外に差別化がない、専門性不要、応募倍率が極端に高い、顧客対応・納品管理の固定コストが報酬に対して大きい案件。AI自動化率95%でも利益が出なければ意味がない。

**Creation より Transformation を優先**（2026-09-13、ChatGPT市場調査より）：ゼロから作る仕事（Creation）より、既存材料を変換・整理・検品する仕事（Transformation）を初期受注では優先する。Input/Outputが明確なのでSkill化しやすく、品質のブレも小さい。具体例：PDF→Word、PDF→Excel、AI文字起こし→議事録、既存文章→リライト、AI骨子→PowerPoint、CSV→整理済CSV、Data A↔Data B→差分チェック。

## ② 案件の適性判定（危険信号 → スコアリング → Hard Gate）

**危険信号チェック（1つでも当てはまれば要注意・見送り推奨）**
- LINE/ChatWork/Slack等プラットフォーム外ツールへの早期誘導
- 相場から極端に外れた低単価（例：データ入力で時給800円未満）
- 家族構成・収入・銀行口座など業務に無関係な個人情報を聞いてくる
- 「詳細は面談で」など仕事内容が曖昧、募集人数が不自然に多い
- 依頼者の評価が0〜5件以下（新規/作り直しの可能性）、低評価に「報酬未払い」「音信不通」の記載がある
- 正式発注前に納品を要求してくる

**Job Scoutスコアリング（危険信号が無ければ実施）**：以下6軸を各0〜5点で採点、合計30点満点
1. Revenue（報酬の大きさ）
2. Automation（AIでどこまで完結できるか）
3. Reuse（既存スキル・過去成果物を再利用できるか）
4. Proof（実績・レビューとして使えるか）
5. Fit（自分の実務経験との相性）
6. Expansion（類似案件・上位商品への横展開余地）

基準：24〜30＝強い候補／18〜23＝条件付き候補／12〜17＝学習目的以外は見送り／0〜11＝原則見送り

**Competition Penalty**（応募倍率＝応募者数／募集人数）：0〜5倍=0、5〜15倍=−1、15〜30倍=−2、30〜60倍=−3、60倍超=−5（スコアから減算）

**Hard Gate**（いずれかを満たすこと）
- 単発：期待粗利3,000円以上 **かつ** 人間作業60分以内が目標
- 継続：月期待粗利20,000円以上
- 戦略案件：粗利が低くても「強い実績」「Skill開発」「上位商品化」のうち2つ以上を満たす

判定結果は「◎やるべき／△条件次第／✕見送り」とスコア内訳を一言コメント付きで返す。既存スキルとの相性（[[pm-ai-kit]]の議事録整理、[[research-kit]]のリサーチ、[[job-hunt-kit]]の添削）もここで確認する。

**運用上の例外（ユーザー確定・2026-09-12）**：[spot-consulting/出品文_議事録整理代行.md](../../../spot-consulting/出品文_議事録整理代行.md)は2,000円〜のまま継続する。単発Hard Gateの粗利3,000円基準は額面では下回るが、実績ゼロ期の「損して得取れ」戦略として意図的な例外と位置づける（Hard Gateの「戦略案件」条件——強い実績・Skill開発・上位商品化のうち2つ以上——に該当する運用とみなす）。レビューが一定数貯まったら3,000円以上への値上げを検討する。

## ③ 経済性評価（案件ごとの期待値判断に使う）

```
Expected Profit = (報酬 × 推定受注確率) − 人間作業時間価値 − 外部費用
Skill Investment Value = Expected Profit + 次回削減時間価値 + 実績価値 + 商品化価値
```

案件の単価だけでなく「この仕事をやると次の仕事がどれだけ楽になるか」で評価する。迷ったらSkill Investment Valueが高い方を優先する。

**判断の優先順位（2026-09-13、ChatGPT市場調査より）**：案件単価 → AI自動化率 → Human Minutes → **Exception Rate（例外率）**。

大量案件（件数が多い案件）では、自動化率そのものより「例外率」が利益を決める。同じ件数でも自動化率がわずかに違うだけで、人間の確認作業量は大きく変わる：
- 10,000件で自動化率99%（例外率1%）→ 人間確認100件
- 10,000件で自動化率95%（例外率5%）→ 人間確認500件

案件を見るときは「自動化率が高いか」だけでなく「残り数%の例外にどれだけ人間の時間を取られるか」を必ず見積もる。

**税務メモ**：会社員が本業を持つ場合、副業所得（売上−必要経費）が年間20万円を超えたら確定申告が必須（本業が無い場合は基礎控除48万円が基準）。所得税の申告が不要でも住民税の申告が別途必要になるケースが多い。`spot-consulting/収益トラッカー.md`に売上・経費を記録しておくと、申告要否の判断がしやすくなる。

## ④ 提案文の作成

採用される提案文の核心は「冒頭の課題復唱＋4パート構成＋個別カスタマイズ」。テンプレ丸出し・使い回しが最大の不採用要因なので、必ず案件文の内容を踏まえて書く。

適性◎の案件について、以下4パートを含む提案文ドラフトを作る：
1. **あいさつ＋課題復唱**：依頼内容をどう理解したかを自分の言葉で一言示す（丸写しにしない）
2. **経歴・対応範囲**：実績・強みを一言（ハンドルネーム運用の場合、経歴の詳細は出さず「〇〇分野の整理・言語化を得意としています」程度に留める。[[feedback_handle_name_anonymity]]の方針に従う）
3. **稼働時間・納期**：1日どれくらい対応できるか、納期の目安。単価は金額だけでなく「仕事の進め方」もセットで伝えると通りやすい。始めたばかりの段階は時給700〜900円程度の控えめな単価で信頼構築を優先し、実績が積み上がってから交渉する
4. **締め**：納期厳守・責任を持って納品する旨

実績が少ない段階では、経験不足を「誠実な姿勢・学ぶ意欲」でカバーする書き方にする。

**送信はユーザーが行う。**

## ⑤ 受注後の納品物作成

まず案件内容に応じてヒアリング項目を確認する（依頼者に確認するか、募集文から読み取る）。必須5項目：**基本情報／課題／予算・納期／ゴール／意思決定者**。質問数は15〜20問程度に絞る。

案件のジャンルに応じて、既存スキルを呼び出す：
- 議事録・要約系 → [[pm-ai-kit]]。決定事項・TODO（担当者・期限）・次回アジェンダまで一体化して整理する（単純な文字起こし清書で終わらせない）
- リサーチ・調査系 → [[research-kit]]
- 添削・文章系 → [[job-hunt-kit]]の型を流用、または直接執筆
- 資料構成・パワポ系 → 「背景・課題提示→解決策→効果→実行計画」の順で構成し、結論を先に書く。デザイン指示はフォント視認性重視・配色4色以内・文章は短く簡潔に、を基本にする

納品前に、必ずユーザーに最終確認してもらってからアップロードする。

## ⑥ 品質管理（共通QAルール＋AIっぽさ対策）

- 入力にない実績・数字を生成しない／出典のない数字を断定しない
- 固有名詞・日付・金額を確認する／要件との差分を自動チェックする
- クライアント固有のルール（用語・フォーマット等）は案件ごとにメモして再利用する
- 個人情報は必要最小限に留め、外部送信前は必ずHuman Gateを通す
- ココナラのトークルームは取引目的以外に使わない・外部公開しない。送信メッセージは原則取り消し不可なので送信前に必ず確認する

**AIっぽさ対策の技術的背景**：AI検出ツールは主に「Perplexity（予測しにくさ）」と「Burstiness（文の長さ・構文のばらつき）」を見ている。短文と長文を混在させ、構文パターンを変えるなど、意図的な"ばらつき"を作ることが語尾・接続詞の言い換え以上に効くことがある。

**AIっぽさ対策**（原因は語尾・接続詞・主語・抽象度・構成の5要素に集約される。[[note-editor]]のチェックリストと共通）：
1. 具体的なエピソード・固有名詞・数字を、一般論より先に出す（抽象度を下げる）
2. 同じ語尾・接続詞（「また、」「さらに、」「〜です／〜ます」の連続等）の連続を崩す。体言止めや会話的な揺れを時々混ぜる
3. 箇条書きに頼りすぎず、文脈の流れで自然につなぐ
4. 発言の直接転記ではなく、要点・数字優先で読み手基準に再構成する
5. **最後に必ず人間（ユーザー）が目視で確認・微修正してから納品する**

## Common Core構想（将来設計・2026-09-13、ChatGPT提案）

案件が増えてきたら、①〜⑨の各手順を案件ジャンルごとに個別に持つのではなく、**Common Core（共通の型）＋ Domain Skill（案件ジャンル別の中身）＋ Client Profile（顧客ごとの個別設定）** の3層に整理する。

Common Coreのフロー：
```
Input Contract（依頼内容の確定）
→ Fact Lock（事実関係の固定。後から覆らない前提を確認）
→ Economics Gate（②③のスコアリング・Hard Gate）
→ Domain Skill（⑤で呼び出す pm-ai-kit / research-kit / job-hunt-kit 等）
→ Deterministic QA（⑥の機械的チェック：数字・固有名詞の一致確認）
→ Semantic QA（⑥のAIっぽさ対策等、意味面のチェック）
→ Severity Routing（見つかった問題を「軽微」「要修正」「致命的」に振り分け）
→ Exception Queue（自動処理できなかった/判断に迷った項目を溜めておく）
→ Human Gate（人間の最終確認）
→ Delivery QA（納品直前の最終チェック）
→ Abstracted Learning（⑨のLearning Loop）
```

**Client Profileの境界**（既存の匿名化ルールと一致）：
- Public（`.claude/skills/`に置いてよい）：汎用ルール・Skill本体・チェックリスト・匿名化済みテストケース
- Private（`knowledge/`や案件フォルダに留める。Public repoに出さない）：顧客名・実ファイル・顧客固有の用語辞書・文体・納品ルール・実案件データ

**現時点の位置づけ**：これは実案件が増えてきた段階で採用する設計思想。実案件0件の今は、既存の②〜⑩のシンプルな手順のまま進めてよい。件数が増えて「毎回同じような判断・チェックを繰り返している」と感じたら、この構造への移行を検討する。

## ⑦ 出品・応募のコツ（`knowledge/gig-work-research.md`から反映）

- 出品メニュー名は具体的に絞る（「資料作成します」ではなく「議事録→提案書パワポ化、専用」のように用途限定）。タイトルは**「検索キーワード＋ベネフィット」**のセットで作る（用途限定の言葉＋得られる価値の両方を入れる）
- 初心者段階では1件受注に20〜30件応募が目安。最初から高打率を期待しない
- プロフィール・提案文の実績は数字で示す（「経験あります」ではなく「◯件対応」）
- ココナラは販売手数料22%。価格は手取りベースで採算計算する
- リピート化の鍵は基本に忠実であること：納期厳守、遅れそうなら早めに連絡、返信は12時間以内（遅くとも24時間以内）。単発の質を上げることが次の案件探しコストを下げる
- ココナラの納品時は「気に入っていただけましたら、簡単なもので構いませんので評価をいただけると嬉しいです」の一言を添える（評価は自動で付かず、購入者側から依頼しないと忘れられがち）
- クラウドワークスは契約完了後にメッセージだけで追加業務を進めるとガイドライン違反になり得る。継続してほしい場合は新しい契約を結び直すか「マイルストーン払い」を使う

## ⑨ Learning Loop（納品後の学習・再発防止）

納品後に修正が入ったら、以下の順で記録する：

```
修正内容（correction） → 理由（reason） → 再利用可能なルール（reusable_rule） → スキル改善（skill_update）
```

`spot-consulting/収益トラッカー.md`の備考欄、または該当スキル（[[pm-ai-kit]]等）・[[skill-scout]]のbacklogに書き残し、同じ修正を次の案件で繰り返さないようにする。

**ChatGPTへの逆流（2026-09-13追加）**：一般化・匿名化した実行知見（例：「議事録整理系はヒアリング込みで平均◯分、自動化率◯割」「時給換算◯円以下の案件は割に合わない」「この種の依頼者は修正回数が多い傾向」）は、`knowledge/a3-execution-learnings.md`（無ければ新規作成、日付見出しで追記）にも書く。このファイルはPublic repoで追跡され、ChatGPT側が案件探索条件を更新する際の参照先になる。
