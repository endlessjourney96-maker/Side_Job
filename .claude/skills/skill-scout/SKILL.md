# スキル化考案チーム

このプロジェクトで繰り返し発生している作業を見つけ、汎用スキル（`.claude/skills/`配下のSKILL.md）に昇格させていくための仕組み。バックログは `.claude/skills/skill-scout/backlog.md` に貯める。

**運用は2段階**：

## ① 都度メモ型（デフォルトで常に動かす）

会話の中で以下のようなパターンに気づいたら、その場で `backlog.md` に追記する。ユーザーに毎回確認を求める必要はなく、気づいた時点で追記してよい（実際にスキル化するかはユーザー判断）。

**気づくべきサイン（Skill化判断ルール）**：以下のどれかに該当したらSkill候補とする。
- 同じ作業・構成・型のファイルやメッセージを3回以上作っている（例：企業別面接対策資料、日報、比較検討表）
- 毎回同じ判断基準を使っている
- 10分以上かかる作業をAIで大きく短縮できる
- 他人にも再利用できる（自分だけの事情に依存しない）
- チェック漏れが発生しやすい作業である
- AIに任せても品質が安定する
- 複数のAI・ツール（メール・Excel・カレンダー等）を組み合わせる価値がある
- 「前もこんな感じでお願いしたような」とユーザーが言っている
- 既存スキルと似ているが、微妙に対象や粒度が違う作業

ただし「便利そう」というだけではSkill化しない。実際の利用頻度とROIを優先する。

**backlog.mdへの追記フォーマット**
```
## YYYY-MM-DD
- **[候補名]** 概要（何をどう汎用化できそうか）
  - きっかけ：どの作業からこの気づきを得たか
  - ステータス：未検討 / 検討中 / スキル化済み（→ 実際のskill名）
```

## ② 「いつものルーティーン」（1日1回、schedule で自動実行）

呼びかけ（「いつものルーティーンお願い」等）でも、schedule による毎日の自動実行でも、同じ4ステップを回す。

**Step 1: 調査**
Web検索で「転職活動」「note・コンテンツ制作」「個人の業務効率」「チームの業務効率」の4カテゴリ（`categories.md`参照）それぞれについて、新しいClaude Codeスキル・MCP連携・業務自動化事例を調べる。前回までに`backlog.md`に載せた候補と重複するものは除く。

**Step 2: 分析**
- 調査結果と、直近の会話・作業ログ（①の「気づくべきサイン」）を照らし合わせ、`backlog.md`の「ネタ帳」に新規候補を追記する
- `categories.md`の「未導入・検討中」に反映する
- `スキル活用一覧.xlsx`（プロジェクト直下）の「スキル一覧」シートに、新規候補を行として追加する（列：カテゴリ／スキル名／概要／活用シーン／おすすめ度(1-5)／種別(自動化・効率化)／ステータス／出典備考）。既存行の情報が古ければ更新する
- `knowledge/inbox/chatgpt/` 配下に未処理（frontmatterやステータス行が「処理済み」になっていない）のMarkdownファイルがあれば、下記「ChatGPT Knowledge Inboxの処理」に従って振り分ける
- `knowledge/inbox/notebooklm/` 配下に未処理のMarkdownファイルがあれば、下記「NotebookLM Knowledge Inboxの処理」に従って振り分ける

### ChatGPT Knowledge Inboxの処理

ユーザーはChatGPTとの会話から得た知見を `knowledge/inbox/chatgpt/YYYY-MM-DD.md` として都度渡してくる。読んだら保存するだけでなく、必ず以下を行う：

1. 既存Skill（`job-hunt-kit`, `research-kit`, `pm-ai-kit`, `note-*` 等）に統合できる内容か確認する
2. 重複するSkill候補が`backlog.md`に無いか確認する
3. **ユーザー固有の事実**（例：「〇〇社が第一志望」「年収目安〇〇万円」）は `knowledge/user-profile.md` に書く
4. **誰でも使える型・判断ルール**（例：「面接後に志望度・懸念・次回確認事項を整理する」）は該当するSKILL.mdに追記するか、`backlog.md`に新規Skill候補として登録する
5. **失敗事例・注意点**（例：PDFマスキングの失敗、ZIP運用の文字化け対策）は `knowledge/lessons-learned.md` に追記する
6. 新規Skill候補は `スキル活用一覧.xlsx` にも行を追加する
7. 既存の知見と矛盾する内容が来た場合は新しい情報を優先し、古い情報は削除せず「（deprecated: YYYY-MM-DD時点の情報。YYYY-MM-DDに更新）」のように残す
8. 処理が終わったら、inboxファイル冒頭に「処理ステータス: 処理済み（→ 振り分け先を記載）」を追記する（同じファイルを二重に処理しないため）

**重要な分離原則**：ユーザー固有情報と汎用Skillを混在させない。迷ったら「他の人が読んでも意味が通るか」で判断する（通れば汎用Skill、通らなければuser-profile）。

### ChatGPTとの3つの情報経路（2026-09-13確定）

ChatGPTとの間には目的の違う3つの経路がある。混同しないこと。

| 経路 | 方向 | 中身 | Public/Private |
|---|---|---|---|
| `knowledge/inbox/chatgpt/YYYY-MM-DD.md` | ChatGPT → Claude Code | 方針・市場知見・Skill改善案・次の検証事項 | Private |
| `knowledge/outbox/chatgpt/YYYY-MM-DD.md` | Claude Code → ChatGPT | その日Claude Code側で起きた全体状況・意思決定・変更点（差分型） | Private |
| `knowledge/a3-execution-learnings.md` | A-3班(gig-work-kit) → ChatGPT | 実案件から得た再利用可能・匿名化済みの実行知見 | **Public**（Side_Job repoで追跡） |

### Outbox（Claude Code → ChatGPT）の作り方

**タイミング**：その日の作業終了時（目安22〜23時）。skill-scoutの朝7時ルーティンと時間帯が重ならないようにする（「前日まとめ」か「当日開始時点」かが曖昧になるのを避けるため）。

**差分型にする**：毎回全情報を再要約しない。前日のoutboxとの差分（今日新しく起きたことだけ）を書く。以下の6項目フォーマットを使う：

```markdown
# Claude Code → ChatGPT Daily Handoff
date: YYYY-MM-DD

## 1. 今日変わったこと
- 新規Skill / Agent変更 / 新規ツール / ワークフロー変更

## 2. 実行結果
- 成功 / 失敗 / 実測時間 / 品質上の問題

## 3. 新しく得た知見
- 市場 / 顧客 / 自動化 / QA

## 4. PM判断・方針変更
- 優先順位変更 / やめたこと / 新しく始めたこと

## 5. ChatGPTに共有・相談したいこと
- 市場調査してほしい / 別視点で評価してほしい / Skill設計をレビューしてほしい

## 6. Public / Private
- Public化したもの / Privateのまま保持するもの
```

何も特筆すべき変化がなかった日は、無理に作らなくてよい（空のoutboxは意味がない）。

**運用方法（2026-09-13時点）**：完全自動連携はまだしない。実案件がまだ少ないため、「Claude Codeが差分Markdownを生成 → 必要な日だけユーザーが手動でChatGPTに貼る → ChatGPTの回答を`inbox/chatgpt/`に貼ってもらう」で十分。案件数が増えて貼り付け自体が負担になった段階で自動化を検討する。

### NotebookLM Knowledge Inboxの処理

役割分担：**NotebookLM＝大量の資料を読み込んで要約する係、Claude Code＝その要約を受け取って判断・実行する係**。PDF・記事・動画などの一次資料を大量に読ませるのはNotebookLM側で行ってもらい、そこで生成した要約・Q&A・Audio Overviewの書き起こし等を `knowledge/inbox/notebooklm/YYYY-MM-DD.md` として都度渡してもらう。

処理の流れはChatGPT Inboxとほぼ同じだが、NotebookLM由来は「外部の一次情報の要約」という性質が強いため、次の点を意識する：

1. 既存Skill（`job-hunt-kit`, `research-kit`, `note-*` 等）に統合できる内容か確認する
2. 重複するSkill候補が`backlog.md`に無いか確認する
3. **ユーザー固有の事実**は `knowledge/user-profile.md` に書く（NotebookLM由来では出現頻度は低いはず）
4. **誰でも使える型・判断ルール・業界知識**は該当するSKILL.mdに追記するか、`backlog.md`に新規Skill候補として登録する
5. **note記事のネタになりそうな情報**（業界動向、統計、トレンド）は、要点を保持したまま`research-kit`や`note-research`が使える形で整理し、記事化自体は`note-boss`チームに委ねる
6. **失敗事例・注意点**は `knowledge/lessons-learned.md` に追記する
7. 新規Skill候補は `スキル活用一覧.xlsx` にも行を追加する
8. 既存の知見と矛盾する内容が来た場合は新しい情報を優先し、古い情報はdeprecatedとして残す
9. 処理が終わったら、inboxファイル冒頭に「処理ステータス: 処理済み（→ 振り分け先を記載）」を追記する

**注意**：`knowledge/inbox/`配下はPublicリポジトリの`.gitignore`許可リストに含まれていない（デフォルトで除外）。NotebookLMに読み込ませる資料や出力に、転職活動・実案件など公開したくない情報が混ざっている可能性があるため、意図的にこのままにする。

**Step 3: 作成（ドラフトまで）**
- `backlog.md`で★（有望）がついている候補、または3回以上使い回されている作業パターンについて、`pm-ai-kit`と同じ`用途/やり方/プロンプト/ポイント`構成でSKILL.mdドラフトを作る
- **本番の`.claude/skills/<name>/`には置かず**、`.claude/skills/skill-scout/drafts/<name>/SKILL.md`として保存する（ユーザー確認前に有効なスキルとして登録されないようにするため）
- ドラフトを作った旨と概要を`backlog.md`のステータスに「ドラフト作成済み（→ drafts/<name>）」として記録する

**Step 4: レビュー**
- 導入済みスキル（`categories.md`の各表）を一覧し、直近の会話で実際に使われたか・内容が古くなっていないかを軽くチェックする
- 明らかに重複している、または使われていないスキルがあれば`backlog.md`に「要整理」として記録する（勝手に削除はしない）

**実行後の報告**：4ステップの結果を短くまとめてユーザーに報告する。自動実行（schedule経由）の場合も同様に報告する。**ドラフトの本採用（`drafts/`から`.claude/skills/`本体への昇格）は必ずユーザー確認を経てから行う**——ここだけは完全自動化しない。

**注意**：Web検索を伴う自動実行は `schedule` スキルで頻度・時間帯を設定した場合のみ毎日動く。呼びかけ起動の場合はいつでもこのSTEP1〜4を実行してよい。

## Public repoでの運用ルール（必読・2026-09-12制定）

このプロジェクトのスキル群は `endlessjourney96-maker/Side_Job` という **Public** リポジトリで管理・自動更新されている。`.gitignore`は`.claude/skills/**`など公開前提のパスだけを許可リストに入れているが、それだけに頼らず以下を必ず守る。

1. **実案件の原本・顧客データはこのリポジトリに絶対に入れない**（`gig-work-kit`の受託案件、`spot-consulting-kit`の相談内容など）。募集文の引用、クライアントとのやり取りの生データ、納品物そのものは対象外。
2. **ケース学習（Learning Loop等）を残す場合は必ず匿名化する**：「〇〇社」→「顧客A」、「9/12 14:00の打ち合わせ」→「60分会議」のように、具体的な日時・固有名詞・特定できる情報を一般化してから`backlog.md`や各SKILL.mdに書く。
3. **外部から取得したスキル・コードを取り込む場合は、Public再配布可能なライセンスか確認する**（例：`mcp-builder`等にはLICENSE.txtが同梱されている。MIT/Apache-2.0等の寛容なライセンスなら通常問題ないが、確認できない・改変再配布を禁じるライセンスのものは`drafts/`にも置かず、`backlog.md`に出典だけメモしてユーザーに判断を仰ぐ）。
4. **commit前に必ず `python .claude/skills/skill-scout/scripts/check_secrets.py` を実行する**（メールアドレス・電話番号・郵便番号・APIキー/トークン・秘密鍵・`.env`ファイル名などを機械的にチェックする）。検出があれば**そのファイルの変更をコミットに含めず**、ユーザーに報告する。このスクリプトは正規表現ベースなので、企業名・顧客名など機械的に検出できないものは目視でも確認する。
5. ローカルでは `git config core.hooksPath .githooks` を一度設定しておくと、コミット時に自動でこのチェックが走る（`.githooks/pre-commit`）。

過去に一度pushした内容は、削除してもGit履歴・fork・検索インデックスに残り得る。「後から消せば戻る」とは考えず、迷ったら載せない。

## 候補をスキルへ昇格させる手順

1. `backlog.md` の候補について、実際の作業ログ（該当フォルダのファイル群など）を数点確認し、共通する「型」を抽出する
2. 既存スキル（`pm-ai-kit` 等）のフォーマットに倣い、`用途 / やり方 / プロンプト / ポイント` の構成で `.claude/skills/<新スキル名>/SKILL.md` を作成する
3. 外部由来の候補なら、上記「Public repoでの運用ルール」に従いライセンスを確認する
4. `backlog.md` 側のステータスを「スキル化済み（→ 実際のskill名）」に更新する

新規スキル作成の相談ペースは既存の `note-boss` チーム構成（リサーチ→企画→執筆→編集→集客のように役割分担する形）を参考にしてよいが、この用途では役割分担するほどの規模はまだないため、まずは単一スキルとして作成する運用でよい。
